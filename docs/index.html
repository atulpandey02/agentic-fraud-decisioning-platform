A process record, not a product pitch

An AI agent helped build an AI agent system. Here is what supervising it actually looked like.

This is the story behind a fraud-decisioning platform — a LangGraph agent team that reads transaction features and decides ALLOW / BLOCK / ESCALATE. Partway through, an autonomous coding agent (Claude Code) was brought in to build Phases 4–7 and then harden the whole system. The interesting part isn’t just what got built. It’s the supervision pattern: bounded tasks, self-reports read critically, claims cross-checked, and a running count of the times “done” didn’t survive scrutiny.

The meta-story

An agent, building an agent, watched by a human

The platform’s core deliverable is itself an agent: a supervisor-pattern LangGraph team where a router LLM dispatches specialist agents (features, risk, policy retrieval, decision) over a shared blackboard, with hard invariants enforced in code — “no decision without policy grounding” is a structural rule, not a prompt suggestion. Phases 1–3 (streaming features, RAG retrieval, the first ReAct agent) were built by the human with a conversational assistant. From Phase 4 on, an autonomous coding agent did the building — under explicit, repeated supervision.

That made the project a live experiment in a question the industry keeps asking abstractly: how much can you trust an autonomous agent’s own account of its work? The honest answer recorded here: quite a lot when its claims come with command output — and not at all when they don’t. Several items reported as complete did not survive independent verification (see Field Notes #4 and the six audit fixes in the timeline).

№1

The security bug found twice, on two different code paths

secondary roles

During Priority 1 (security), the BI dashboard connected to Snowflake with role="BI_ROLE" — a role with no grant on the PII schema — and a live check showed it could still read RAW.FACT_TRANSACTIONS. The cause: Snowflake activates all of a user’s granted roles as “secondary roles” by default. The operator’s own ACCOUNTADMIN rode along silently and overrode the restriction. Picking the right primary role restricted nothing; the fix was USE SECONDARY ROLES NONE plus a startup assertion that the session is genuinely single-role.

Then it happened again. In a later round — the post-hardening audit-fix pass, while proving the feature pipeline’s startup probe could run under PIPELINE_ROLE — the same class of bug surfaced on a completely different code path: PIPELINE_ROLE could read DECISIONS, a schema it had no grant on, through the same secondary-roles mechanism. Same fix, second location, found by the agent’s own least-privilege test.

Evidence
CURRENT_SECONDARY_ROLES() returned value “ALL” (including ACCOUNTADMIN and ORGADMIN) on a plain role="BI_ROLE" connection; after the fix it returns an empty set, and the RAW read is denied while legitimate reads still work.
Commits

Lesson generalized: when one instance of a bug class is found, sweep every similar code path for the same mistake instead of assuming it was a one-off. The second instance was only caught because the later round tested least privilege directly rather than trusting the role parameter.
№2

Three wrong dependency guesses in a row — then a different failure in the same place

dependencies

Setting up the LangGraph agent stack, three consecutive attempts to pin exact versions of langgraph / langchain-groq / langsmith were wrong. The two that are documented in the repo’s own file comments: langchain-groq==0.2.10 named a version that did not exist, and langsmith>=0.2.0 directly contradicted what langchain-core actually required. The correction wasn’t a fourth guess — it was to stop guessing: read pip’s real resolver output (which lists every version that actually exists) and let the resolver pick, then pin what was verified working.

The sequel came much later, in the independent audit: the lockfile that made everything reproducible locally had been frozen on macOS, and a genuinely clean Linux CI install failed on it three separate ways (a range contradiction, a packaging version conflict via an old Streamlit cap, and CUDA-variant torch on CPU runners). Local tests were green the whole time. The lock was regenerated on Linux with CPU torch, and the exact CI command was proven in a fresh container.

Evidence
The repo’s requirements_agents.txt header documented the failed guesses in place; audit fix 973c5fc carries the clean-environment proof (fresh python:3.10 container → install OK, pip check clean).
Lesson generalized: “works on my machine” and “works in a clean environment” are two different claims, and each needs its own test. Version numbers are facts to look up, not plausibilities to recall.
№3

The geo-flagging investigation: a three-part root cause, not one bug

44.4% → 26.6%

The streaming scorer was flagging 44.4% of ~1M transactions for review, against a 15% injected fraud rate (17.3% measured in the table) — roughly 3× over-flagging. The rule of the round: no fix without an investigation first. The investigation (run as SQL against the full 999,878-row history) attributed 75% of all flags to a single rule — “geo distance ≥ 475 km” — operating at 17.3% precision, i.e. no better than the base rate. Underneath sat three stacked causes:

Cause 1
Wrong concept. The rule checked raw distance; the documented design concept was implied travel speed (>900 km/h = physically impossible). 475 km is a domestic road trip, not impossible travel.
Cause 2
Out-of-order data. 80% of far-distance legitimate rows had a negative time delta — the “previous location” was chronologically in the future, an artifact of randomized backfill replay.
Cause 3
State poisoning. 99% of affected users (9,927 of 10,000) also had a GEO_JUMP fraud whose foreign location became their new baseline — so their next legitimate purchase at home looked like a second impossible jump.
Outcome
Fix addressed all three (speed-based composite rule + ordering guard + poisoning guard). Simulated on full history: flag rate 44.4% → 26.6%, precision 33.3% → 52.6%, GEO_JUMP recall held (99.2% → 98.9%). The report was required to say “meaningfully improved, still over-flagging by ~1.5×” — not “fixed”.

№4

An independent audit contradicted an “approved as complete” item

policy ≠ control

Priority 1 included the item “define redaction, retention, and access controls for prompts, traces, names, locations…”. It was reported complete — and approved — on the strength of a written policy document (DATA_GOVERNANCE.md) describing what should be protected. A later independent, read-only audit checked the running system instead of the paperwork and found that no redaction code existed at all: the user-history tool returned real names and home locations from DIM_USERS, and the trace writer persisted them verbatim into audit storage on every run.

The correction (audit fix #2) built an actual TraceRedactor that runs before every insert — hashing structured PII to stable pseudonyms and scrubbing quoted names from free-text reasoning — plus a test asserting that full_name can never appear in a persisted field, and a live write/read-back proof against the real database.

Evidence
Live proof in the fix: a trace containing a name and city was written, the persisted rows were read back — name and city absent, [REDACTED:…] tokens present.
Commits
6368e20 (explicitly labeled a correction to a previously-approved item)
Lesson generalized: a claim can be technically true (“a document exists”) and false in the sense that matters (“nothing protects the data”). Approvals should attach to controls demonstrated in the running system, not to artifacts about them. This was the clearest trust-calibration moment in the whole project.
№5

A “clean” metric caught before it became a fact

precision 1.0

A 50-transaction evaluation run hit the LLM API’s free-tier daily token ceiling after 14 transactions. Salvaging metrics from the completed portion produced “precision 1.0” next to “recall 0.50” — numbers that look citable. On inspection, the completed sample contained zero legitimate transactions (the stratified sample wasn’t interleaved, so the fraud half ran first). With no legitimate transaction present, a false positive was impossible: precision computed to 1.0 vacuously, and the false-positive rate was literally undefined (0÷0). The number was relabeled instead of reported, and the sampler was fixed to interleave strata so any partial run stays balanced.

Evidence
Confusion matrix of the completed sample: TP 6 · FP 0 · FN 6 · TN 0 — every completed row was ground-truth fraud.
Commits
d041e92 (interleaved sampling + per-transaction resilience + honest RUN INCOMPLETE labeling)
Interactive · why that 1.0 meant nothing
Lesson generalized: before repeating a metric, ask what data it was computed on and whether the failure mode it measures was even possible in that sample. A perfect score on a sample that cannot produce the error is not evidence — it’s an absence of opportunity.
Judgment calls

Decisions made by reasoning, not convention

Two of these are notable for being decisions not to adopt something fashionable. Source tags mark where each rationale is recorded.

adopted

ReAct over Plan-and-Execute / Reflection

The number of tool calls genuinely varies per transaction: a clear-cut case needs no user-history lookup, a borderline one needs all three tools. A fixed plan can’t adapt to that without paying latency on the easy cases; ReAct decides as it observes.

source: agent design docstrings in the codebase + design discussions
adopted

LangGraph over CrewAI

Two specific requirements sat squarely in LangGraph’s strengths: first-class cycles (the ReAct loop is a cycle) and node-level human-in-the-loop interrupts (needed for the governance approval tiers). Not a judgment that CrewAI is worse — a fit to two named requirements.

source: design discussions (chat) — as recorded in PROJECT_NARRATIVE.md
adopted

Weaviate over Pinecone

Verified, not assumed: Pinecone’s free tier did support hybrid search — but its sparse/dense score balancing needed manual rebalancing, while Weaviate’s hybrid fusion is native. The deciding fact was checked before it was believed.

source: retrieval-layer docstrings in the codebase + design discussions
not adopted

A2A protocol

A real, current standard — for cross-organization agent interoperability. Every agent here is internally owned, one team, one framework. There was no problem for it to solve yet, so it wasn’t added.

source: design discussions (chat) — as recorded in PROJECT_NARRATIVE.md
not adopted

Factory pattern

Considered and rejected for the same reason: it earns its place only when there’s a genuine branching decision about which class to instantiate. None existed at the time it was considered.

source: design discussions (chat) — as recorded in PROJECT_NARRATIVE.md

Read before being impressed

Honest caveats

  • This is a learning and portfolio project on synthetic data — not a deployed commercial fraud system. Every transaction, user, and fraud pattern was generated.
  • Evaluation samples have been small — as few as 6 transactions in one round, and the larger run completed only 14 of 50 before an API budget ceiling. No real statistical confidence has been established yet, and nothing on this page should be read as implying otherwise.
  • Not everything the coding agent reported as “done” survived scrutiny. Several rounds required corrections after independent verification found gaps — six of them in work that had already been approved. That’s presented here deliberately: it is the most useful finding of the whole exercise, not a blemish on it.
