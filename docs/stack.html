Apache Kafka

event transport

The transaction firehose. The synthetic generator produces transactions (including a 10M-row backfill) onto one topic; the Spark feature engine consumes it. Runs in KRaft mode (no Zookeeper), keyed by user_id so every event for a user lands on the same partition — which is what makes per-user windowed aggregation shuffle-friendly downstream. 12 partitions, sized to give 12 parallel Spark tasks; 7-day retention because Snowflake, not Kafka, is the system of record.

Why (as recorded): the design notes in docker-compose.yml record the KRaft choice, the user-keying rationale, and the partition sizing (bumped from 3 to 12 when the user pool scaled to 10,000). No alternative message broker was compared in the repo or narrative — Kafka was the starting assumption, so no invented comparison is offered here.
# docker-compose.yml — the recorded design notes
# KAFKA (KRaft — no Zookeeper)
# user_id as message key → all events per user to same partition
# 12 partitions = 12 parallel Spark tasks (bumped from 3 — at
# 10,000 users, more partitions show real parallel consumption)
# retention 7 days — Snowflake is the audit system of record

Spark Structured Streaming

feature computation

Consumes the Kafka topic and computes per-transaction fraud features in micro-batches: amount z-score against the user's baseline, Haversine geo-distance from Redis state, new-device flag, sliding-window velocity (a second concurrent query), and the two-tier risk score. Uses foreachBatch as the sink because Spark has no native Redis or Snowflake streaming sink — a rationale recorded in the engine's own docstrings. Windows are event-time based on transaction_ts, not processing time (“fraud velocity = what the user DID, not when Spark read it”).

Why (as recorded): the choice is documented by its constraints — event-time sliding windows with watermarks, and maxOffsetsPerTrigger bounding backfill batches. No alternative stream processor was compared in the repo or narrative.
def _read_kafka_stream(self) -> DataFrame:
    return (
        self._spark.readStream
        .format("kafka")
        .option("kafka.bootstrap.servers", self._config.KAFKA_BOOTSTRAP_SERVERS)
        .option("subscribe", self._config.KAFKA_TOPIC)
        .option("startingOffsets", self._config.KAFKA_STARTING_OFFSETS)
        .option("kafka.group.id", self._config.KAFKA_GROUP_ID)
        # Max messages per partition per micro-batch …
        .option("maxOffsetsPerTrigger", 50_000)
        .load()
    )

Redis

online feature store

The low-latency store the agents actually read at decision time. Two key families: user:{id}:features (the full snapshot the agent's get_transaction_features tool fetches) and user:{id}:location (geo state for the next Haversine computation — kept separate so internal pipeline state doesn't pollute agent reads). 24-hour TTL: stale features self-expire.

Real recorded evolution — batch reads over per-row reads: the original loop did one Redis GET per transaction — 10,000 network round trips per micro-batch. The recorded fix replaced it with a single MGET per batch, and the timing was logged explicitly so the fix is observable, not assumed. Redis itself vs another KV store was not compared in the repo or narrative; the recorded engineering is in how it's used.
unique_user_ids = list(set(user_ids))
keys = [f"user:{uid}:location" for uid in unique_user_ids]

try:
    raw_values = self._client.mget(keys)  # ONE round trip
except Exception as e:
    logger.warning(f"Redis MGET batch failed: {e}")
    return {uid: None for uid in unique_user_ids}

Snowflake

warehouse + audit system of record

Four schemas, deliberately split by access domain on day 1: RAW (PII transactions, pipeline-only), DIM (user/device baselines), FEATURES (computed snapshots — 999,878 rows), DECISIONS (agent decisions + full reasoning traces). Role-based access (PIPELINE_ROLE / AGENT_ROLE / BI_ROLE) maps onto those schemas — the boundary at the center of the twice-found secondary-roles bug (Field Note №1).

Why (as recorded): the schema-per-access-domain design principle is written at the top of snowflake/schema.sql; VARIANT columns hold JSON tool inputs/outputs in the trace table. No alternative warehouse was compared in the repo or narrative.
-- snowflake/schema.sql — the recorded design principles
-- Design principles:
--   - Separate schemas per access domain (security + clarity)
--   - RAW: pipeline writes only, no agent access
--   - FEATURES: pipeline writes, agents read
--   - DECISIONS: agents write, BI agent reads
--   - DIM: pipeline writes, agents read (baseline context)

S3 + Snowpipe

bulk ingestion path

The offline write path for feature snapshots: rows buffer in memory across micro-batches, flush as one snappy-compressed Parquet file to S3, and Snowpipe (AUTO_INGEST via SQS) loads it into FACT_FEATURE_SNAPSHOTS — no polling, no manual COPY.

Real recorded replacement: this replaced row-by-row executemany inserts through the Python connector, which the repo records as “taking minutes per micro-batch and becoming the dominant bottleneck in the whole pipeline.” Buffering also addresses the classic “small files problem” — the docstring explains why a 3-row Parquet file every 30 seconds is waste. Source: S3FeatureWriter docstrings — a genuine before/after that actually happened, not a hypothetical comparison.
table = pa.Table.from_pylist(self._buffer)
buf = io.BytesIO()
pq.write_table(table, buf, compression="snappy")
# File naming includes a UUID + timestamp to guarantee uniqueness —
# Snowpipe processes each file exactly once by object key, so
# colliding names would silently drop data.
key = f"{self._config.S3_PREFIX}/features_{timestamp}_{file_id}.parquet"
self._s3_client.put_object(Bucket=self._config.S3_BUCKET, Key=key, Body=buf.getvalue())

Weaviate

vector store / RAG retrieval

Holds the fraud-policy knowledge base: authored policy docs and case studies, chunked by Markdown section, embedded locally (all-MiniLM-L6-v2), and searched with hybrid BM25-plus-vector queries. The agent's get_policy_context tool is a thin wrapper over this, with an optional per-pattern filter.

Real comparison — Weaviate over Pinecone: per the project narrative, it was verified, not assumed, that Pinecone's free tier did support hybrid search — but its sparse/dense score balancing needed manual rebalancing, while Weaviate's fusion is native. The same reasoning is recorded in the code itself: source: PROJECT_NARRATIVE.md “Design decisions” + the hybrid_search docstring quoted below.

LangGraph

agent orchestration

The framework both agent architectures are built on: the Phase 3 single agent is an explicit ReAct StateGraph (built by hand rather than with the create_react_agent prebuilt, specifically to keep the loop mechanics visible), and the Phase 4 multi-agent system is a supervisor graph routing between four specialists. The full mechanical walkthrough lives on the Architecture page.

Real comparison — LangGraph over CrewAI: per the project narrative, two specific requirements decided it: first-class support for cycles (the ReAct loop is a cycle) and node-level human-in-the-loop interrupts (needed for the governance approval tiers) — “not because CrewAI is worse, but because those two specific requirements sit in LangGraph's strengths.” Source: PROJECT_NARRATIVE.md “Design decisions” (chat-side reasoning, presented at the narrative's level of detail).
graph = StateGraph(AgentState)
graph.add_node("agent", self._call_model)

graph.add_node("finalize", self._finalize)

graph.add_edge("tools", "agent")   # the ReAct cycle

Groq (llama-3.3-70b-versatile)

LLM provider

Serves every LLM role in the system: the single agent, the router and four specialists, the NL2SQL generator, and the LLM-as-judge (at temperature 0). Temperature for the agents is 0.1 — the config records why not zero. Groq's free-tier 100K tokens/day ceiling is also a real character in this story: it cut the 50-transaction eval at 14 (Field Note №5).

Why (as recorded): the original config docstring recorded that this exact model was “already proven working in the earlier Agentic DQ Monitor project,” plus a warning that model IDs on inference providers churn fast. The judge sharing the agents' model family is a disclosed limitation, cross-checked by an outcome-agreement metric. No provider bake-off was recorded — continuity from a prior project was the stated reason.
GROQ_API_KEY = _s.llm.groq_api_key

sqlglot

SQL security guardrail

The AST parser behind the BI dashboard's NL2SQL guardrail. LLM-generated SQL is parsed into a syntax tree and validated structurally: single statement, SELECT/CTE shapes only, every table reference fully qualified and allowlisted (the PII schema isn't on the list), dynamic identifiers and table functions rejected, the row cap enforced even when the model writes a bigger LIMIT — and the re-serialized AST is what executes, not the raw model text.

Real recorded replacement: it replaced a regex/keyword validator that genuinely shipped first — and that a table function or IDENTIFIER('RAW…') could walk straight past. The repo's 38 bypass tests were written against exactly those holes before the AST version existed. Source: sql_guard.py docstrings + tests/test_sql_guard.py — an actual predecessor, not a strawman.

Docker Compose

local infrastructure

Runs the whole substrate locally: Kafka (KRaft), Spark master/worker, Redis (with allkeys-lru eviction), Weaviate (vectorizer disabled — embeddings are supplied by our own code), and a Kafka UI. The hardening round pinned every image (one was :latest), added a memory limit and healthcheck to the unpinned service, and left the reasoning in place as comments.

Why (as recorded): reproducibility — the pinning commit records that a :latest tag “makes the stack non-reproducible — a rebuild could silently pull a new UI.” No alternative to Docker Compose was compared in the repo or narrative.
