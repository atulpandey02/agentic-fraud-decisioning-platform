The machinery, not the mythology

Agentic architecture deep dive: how these LangGraph agents actually work

Everything on this page is built from the real code on this branch — the graphs are drawn from _build_graph(), the clickable nodes show the verbatim functions behind them, and the trace replay walks a recorded run, labeling precisely which parts were recorded and which the record doesn't capture. Concepts first, then this system's two architectures.

Part A · Concepts

How LangGraph works — the four ideas everything else builds on

These transfer to any LangGraph system. Each card ends with where the concept shows up in this repo.

1 · Nodes

A node is just a function: it receives the current state and returns a partial update — only the keys it wants to change. Nodes can call an LLM, run a tool, or be pure Python; the graph doesn't care.

In this repo_call_model, ToolNode(ALL_TOOLS) and _finalize in the single agent; _route plus four specialist.run methods in the orchestrator.

2 · Edges

Edges say what runs next. A plain edge is unconditional. Because edges can point backwards, a graph can express a loop — which is exactly what a ReAct agent is: reason → act → observe → reason again.

In this repograph.add_edge("tools", "agent") — the single line that turns a pipeline into a ReAct cycle. (Per the narrative, first-class cycles were one of the two reasons LangGraph was chosen over CrewAI.)

3 · Conditional edges

A router function inspects the state and returns the name of the next node. This is where control-flow decisions live — and it's ordinary code, so you can put hard guarantees here that no prompt can bypass.

In this repo_should_continue (tools or finalize? plus the MAX_REASONING_STEPS cap) and the orchestrator's lambda state: state["next_agent"], which just reads the choice _route already recorded.

4 · State + reducers

State is a TypedDict threaded through every node. When a node returns an update, each field is merged using its reducer. Default: overwrite. Annotated[list, add_messages] makes message updates append — that's how conversation history accumulates across loop iterations instead of being replaced.

In this repomessages: Annotated[list[BaseMessage], add_messages] in both states; the orchestrator adds a second reducer, agents_invoked: Annotated[list, operator.add], so every specialist appends its own name.

Where the two architectures mechanically diverge

    
Each row is verifiable in the two files shown in the diagrams above — this is a code comparison, not a philosophy comparison.

    

      
MechanismSingle agent (ReAct)Multi-agent (supervisor)

      
        
Model judgment
          Everywhere: the same LLM conversation decides which tool to call, when to stop, and what to conclude.
          Routing only. Specialists have no tool-choice autonomy: each does one deterministic tool.invoke(...) in code, then one focused LLM call to interpret it.

        
State shape
          messages is the working memory — tool results exist only as ToolMessages inside the conversation.
          A typed blackboard: feature_findings, elevated_patterns, risk_assessment, policy_guidance — specialists read each other's typed fields; messages is demoted to a narrative log.

        
Reducers
          add_messages only.
          add_messages plus operator.add on agents_invoked — each node appends its name, which is what the router's run-at-most-once check reads.

        
Tool binding
          llm.bind_tools(ALL_TOOLS): the model emits tool_calls; ToolNode executes whatever it asked for.
          Tools are constructor-injected by the orchestrator (one owner of cross-module reuse); specialists call them unconditionally — “letting a model decide to do the only thing it exists to do costs a round-trip for nothing.”

        
The policy invariant
          A prompt instruction: “Always call get_policy_context at least once before deciding” — the model could ignore it.
          Code: _route overrides any attempt to reach decision_agent before policy_agent has run — structurally impossible to violate.

        
Runaway protection
          MAX_REASONING_STEPS = 8: counts AIMessages, forces finalize.
          ORCHESTRATOR_MAX_STEPS = 6: hard-stops in _route before the LLM is even consulted, forcing policy-then-decision.

        
Termination
          Emergent: the model stops requesting tools → conditional edge routes to finalize.
          Structural: routing to the terminal decision_agent node ends the run by graph shape (decision_agent → END).

        
Attribution
          AIMessages are unnamed — the trace writer labels them single_agent.
          Every message carries name= (orchestrator or specialist) — which is exactly what FACT_AGENT_TRACES.agent_name and the HANDOFF step type consume.

  • Model free-text was not recorded for the single-agent run being replayed: the demo printed the
        final structured decision, not the intermediate AIMessage contents. The replay therefore quotes only
        code, prompts, tool docstrings, tool return formats, and recorded run facts — never reconstructed dialogue.
    • 
        
  • Groq-call accounting: the run is recorded as “4 Groq calls” while all three tools fired. Four
        calls can cover three tools only if at least two tools were requested in a single AIMessage (LangChain
        permits multiple tool_calls per message and ToolNode executes them all). The exact
        grouping wasn't recorded, so the replay shows the maximally explicit one-tool-per-turn walk and says so.
    • 
        
  • The policy corpus is stale relative to the code: retrieval/policy_docs/geo_jump.md
        still documents the old hard rule (“normalized geo-distance signal reaches 0.95”), which the geo
        investigation replaced with the speed-or-3000km composite. The RAG documents were never updated after the
        fix. The replayed run predates the fix, so the excerpt shown is what the agent would genuinely have
        retrieved at the time — but a run today would retrieve outdated policy text. Found while building this
        page; disclosed rather than silently corrected.

  • A stale comment in agent.py: the MemorySaver comment still says writing FACT_AGENT_TRACES is
