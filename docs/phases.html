The project, phase by phase

Seven phases — what, with what tools, why this and not that

Every phase gets the exact same four questions, answered separately and labeled — not buried in a narrative: WHAT it does, TOOLS used in that phase specifically, WHY THIS, NOT THAT (the recorded reasoning, quoted from where it was actually written down), and WHAT IF NOT (what the rejected alternative would likely have cost — stated only where a real alternative was actually considered; where none was recorded, that is said plainly). This page answers what and why; the architecture page answers how, mechanically.

Phase 1

Streaming foundation + feature store

done · verified at ~1M rows
What

A synthetic transaction generator (10,000 users, SCD2 DIM_USERS, four injectable fraud patterns, a 10M-row backfill mode) publishes to Kafka; a Spark Structured Streaming engine computes per-transaction fraud features — amount z-score against the user's baseline, Haversine geo-distance from Redis-held last-location state, new-device flag, 15-minute sliding-window velocity, and a two-tier risk score (weighted signals plus hard-rule single-signal overrides). Features land in two places: Redis as the online store (24-hour TTL) and S3 Parquet → Snowpipe → Snowflake FACT_FEATURE_SNAPSHOTS as the audit record. Verified live: 999,878 rows, 443,805 flagged, all flagged rows carrying ground truth.

Tools in this phase
Apache Kafka (KRaft)Spark Structured StreamingRedisS3 + SnowpipeSnowflakeDocker Compose
Why this, not that

The recorded reasoning in this phase is about how the tools are used, not which tools to pick: user_id as the Kafka message key so per-user aggregation is shuffle-friendly; event-time windows on transaction_ts rather than processing time; foreachBatch as the sink because Spark has no native Redis or Snowflake streaming sink; two concurrent Spark queries sharing one session and communicating via Redis; and the two-tier scoring design — weighted judgment plus hard rules where a property must always hold (added Day 4, with its reasoning documented in the engine).

One in-phase choice has a recorded before/after rather than a hypothetical: row-by-row executemany INSERTs to Snowflake were the actual first implementation, and the repo documents replacing them with the S3 Parquet + Snowpipe path (and, similarly, batching Redis reads with MGET to fix an N+1). Details and code snippets are on the stack page.

What if not

No alternative was recorded for Kafka, Spark, Redis, or Snowflake themselves — they were the starting assumptions, and stack.html already discloses this per tool. No invented bake-off is offered here.

The one real, measured counterfactual inside this phase is the write path: the repo kept the row-by-row SnowflakeFeatureWriter as a fallback after replacing it, so "what if not Snowpipe" is answered by the code's own history — per-row round-trips to the warehouse on a streaming workload, which is exactly what got replaced.

Phase 2

Retrieval / RAG layer

done · survived a container restart intact
What

A fraud-policy knowledge base the agents can search: 4 policy documents + 4 case studies (one per fraud pattern, authored for retrieval — H1 = pattern name, H2 sections), chunked by a structure-aware H2 chunker (with a documented prefix-overhead budget fix), embedded with all-MiniLM-L6-v2, and stored in Weaviate as the FraudPolicyChunk collection with native hybrid (BM25 + vector) search and an optional per-pattern filter.

Tools in this phase
Weaviatesentence-transformers (all-MiniLM-L6-v2)custom H2 chunkerDocker Compose (persistent volume)
Why this, not that
Weaviate over Pinecone — a real, verified comparison
"Weaviate over Pinecone for the retrieval layer, after verifying (not assuming) that Pinecone's free tier DID support hybrid search, but that Weaviate's score fusion was native while Pinecone's needed manual rebalancing — a real, verified technical reason, not just a hunch." PROJECT_NARRATIVE.md · "Design decisions" · quoted in full

Note what the record does not claim: it does not say Pinecone lacked hybrid search (it was verified to have it). The recorded difference is narrower — native score fusion versus fusion the project would have had to rebalance by hand.

What if not

Pinecone: per the recorded comparison, hybrid keyword + vector ranking would have worked, but the fusion of the two scores would have been a manually rebalanced knob the project owns and maintains, instead of an engine-native feature. Nothing beyond that was recorded, so nothing beyond that is claimed.

The embedding model: no alternative to all-MiniLM-L6-v2 was recorded — said plainly rather than invented.

Phase 3

Single ReAct agent

done · 2 verified end-to-end runs
What

One LLM agent that decides ALLOW / BLOCK / ESCALATE for a flagged transaction. It runs a ReAct loop built as an explicit LangGraph StateGraph: the model reads the case, calls whichever of its three tools it judges necessary (features, policy, user history), observes, repeats — capped at MAX_REASONING_STEPS = 8 — then a dedicated finalize step restates the conclusion as a typed DecisionOutput. Verified twice end to end: BLOCK / GEO_JUMP / 0.9 and ESCALATE / GEO_JUMP / 0.6, each in 4 Groq calls with all three tools firing.

Tools in this phase
LangGraph (StateGraph · ToolNode · add_messages · MemorySaver)Groq llama-3.3-70b-versatileget_transaction_features → Redisget_policy_context → Weaviateget_user_history → Snowflake DIM
Why this, not that

Three distinct recorded decisions live in this phase. They answer different questions and are easy to conflate — so here they are separately.

Decision 1 — the reasoning pattern: ReAct over Plan-and-Execute or Reflection
"ReAct over Plan-and-Execute or Reflection for the single agent, specifically because the number of tool calls needed genuinely varies per transaction (a clear-cut case needs no history lookup; a borderline one needs all three tools) — Plan-and-Execute's fixed pipeline can't adapt to that without wasting latency on easy cases." PROJECT_NARRATIVE.md · "Design decisions" · quoted in full

This comparison exists in the narrative but never appeared explicitly on the architecture page — it is a different question from Decision 3 below. Fidelity note: the record states the concrete failure mode for Plan-and-Execute (fixed pipeline, wasted latency); for Reflection it records the rejection but no separate, Reflection-specific critique beyond the same variable-tool-count rationale.

Decision 2 — the framework: LangGraph over CrewAI
"LangGraph over CrewAI, specifically because of first-class support for cycles (ReAct's repeated loop) and node-level human-in-the-loop interrupts (needed for the governance/approval tiers) — not because CrewAI is worse, but because those two specific requirements sit in LangGraph's strengths." PROJECT_NARRATIVE.md · "Design decisions" · quoted in full
Decision 3 — the construction: hand-built StateGraph over the create_react_agent prebuilt

A narrower question than Decisions 1–2: having already chosen the ReAct pattern and LangGraph, should the loop be assembled by hand or generated by the one-line helper? The recorded answer, from the agent file's own header:

# Built with StateGraph directly rather than LangGraph's
# create_react_agent prebuilt helper. create_react_agent would
# build the exact same call_model <-> tools loop in one line —
# using it here would hide the mechanics we specifically want
# visible: how the conditional routing works, how the loop
# terminates, how MAX_REASONING_STEPS prevents a runaway agent.
fraud_platform/agents/single_agent/agent.py (verbatim)

This is the decision architecture.html explains — it is not the ReAct-vs-Plan-and-Execute decision, which is why both appear here, labeled apart.

What if not

Plan-and-Execute: the recorded downside is concrete — a fixed plan can't shrink for easy cases, so every clear-cut transaction would pay the full tool budget in latency (and this system's recorded runs really do vary: the supervisor's later verified runs used three tools on one transaction and skipped the history fetch on another).

Reflection: rejected in the same recorded sentence, but no Reflection-specific failure mode was written down — disclosed rather than invented.

CrewAI: per the record, not "worse" — but the two load-bearing requirements (a first-class reasoning cycle, and node-level human-in-the-loop interrupts that Phase 5's approval tiers would need) sit in LangGraph's strengths. Choosing CrewAI would have meant building this system's two defining control-flow features against, rather than with, the framework's grain — that is the extent of what the record supports.

create_react_agent: the same loop in one line, with the mechanics this project specifically wanted visible (routing, termination, the step cap) hidden inside the helper.

Go deeper (the "how"): the clickable ReAct StateGraph — every node loads its verbatim function — and the 10-step trace replay of the recorded BLOCK/GEO_JUMP run, with each step labeled recorded / mechanics / not-recorded.
Phase 4

Multi-agent orchestrator (supervisor pattern)

done · 2 verified runs with different routing
What

The same decision job as Phase 3, restructured: an orchestrator node routes among four specialists — feature_agent, risk_agent, policy_agent, decision_agent — over a shared typed blackboard (MultiAgentState). The router LLM chooses order and skips; code enforces the invariants. Verified with genuinely different routing: a clear-cut case ran feature → policy → decision with risk_agent skipped (ALLOW at 0.8); a borderline GEO_JUMP ran all four (ESCALATE at 0.6).

Tools in this phase
LangGraph (supervisor StateGraph)Groq (structured-output router + 4 specialist calls)Phase 3's three tools, constructor-injectedoperator.add blackboard reducer

Deliberately no new data-access tools: the specialists reuse Phase 3's three tools — "the tools ARE the platform's data-access layer for agents; two copies would drift" (orchestrator.py).

Why this, not that
Why introduce a multi-agent supervisor at all — not just how it differs

Two recorded reasons: task decomposition into specialists, and structural enforcement of invariants the single agent could only be asked to honor. In the orchestrator's own words:

"The single agent interleaved evidence-gathering and deciding inside one conversation; one model juggled every concern with every tool. Here each concern is a SPECIALIST with a focused prompt and exactly the tools it needs, and the model-driven judgment that remains is ROUTING: which specialist runs next, and whether one can be skipped. That split is what makes the system's reasoning inspectable per-concern (Phase 6 traces get an agent_name per step) and extensible per-concern (a fifth specialist is a new node + one line in the router prompt, not a rewrite of a monolithic prompt)." fraud_platform/agents/multi_agent/orchestrator.py · header · verbatim (reflowed from comment lines)

The invariant that makes the point sharpest: policy-before-decision. Phase 3 enforced it with a prompt line ("Always call get_policy_context at least once before deciding") that the model could ignore; Phase 4's router guardrail makes routing to decision_agent without prior policy grounding structurally impossible — the code overrides the model's choice and logs the override.

Why LLM routing with code guardrails — not a fixed pipeline, not pure LLM routing
"A fixed pipeline (feature -> risk -> policy -> decision, always) needs no LLM router at all — but then clear-cut cases pay for a user-history fetch and an extra LLM call they don't need, and the "orchestrator" is just a for-loop wearing a title. Pure LLM routing, by contrast, can skip the policy grounding or ping-pong between specialists. So: the LLM chooses the ORDER and the SKIPS (the judgment part), while code enforces the INVARIANTS (the correctness part) — each specialist runs at most once, policy must run before a decision, and a hard step cap ends a confused run." fraud_platform/agents/multi_agent/orchestrator.py · header · verbatim (reflowed from comment lines)
Fidelity disclosure: there is no standalone "Day 1 blueprint" document in the repo. The recorded framing of when multi-agent beats single-agent lives in orchestrator.py's header docstring (quoted above) and PROJECT_STATUS.md's Phase 4 notes. The Day-1 design decisions that do survive in code references are the AGENT_ROLE access boundary (tools.py: "designed on Day 1") and the per-step agent_name trace column (multi_agent/state.py: "designed for on Day 1").
What if not

Fixed pipeline instead: per the recorded reasoning above — clear-cut cases pay for a user-history fetch and an extra LLM call they don't need. The verified runs show this is not hypothetical: the clear-cut run really did skip risk_agent.

Pure LLM routing instead: per the same record — the router could skip policy grounding or ping-pong between specialists; the guardrail overrides exist precisely because the router was not trusted to always honor the invariants.

A2A protocol (considered, declined):

"A2A protocol deliberately NOT adopted, despite being a real, current standard, because it solves cross-organization agent interoperability and every agent in this system is internally owned, one team, one framework — there was no real problem for it to solve yet." PROJECT_NARRATIVE.md · "Design decisions" · quoted in full

Adopting it would have added protocol machinery for a cross-organization problem this system does not have.

Factory pattern (considered, declined):

"A Factory pattern deliberately NOT added, for the same class of reason — it only earns its place when there's a genuine branching decision about which class to instantiate, and none existed at the time it was considered." PROJECT_NARRATIVE.md · "Design decisions" · quoted in full
The narrative records both declined decisions but does not date them to a phase; they appear here because they are agent-system structure decisions, and Phase 4 is where that structure was built.
Go deeper (the "how"): the clickable supervisor graph with the verbatim _route guardrails and the recorded 2026-07-06 run log, and the 8-row mechanical divergence table — the how-it-differs question is answered there and deliberately not duplicated here.
Phase 5

Governance / human-in-the-loop

done · first phase where decisions became durable
What

The agent decides what should happen (ALLOW / BLOCK / ESCALATE); governance decides how much autonomy that decision gets. A deterministic framework maps (decision, confidence, amount) → a tier — AUTO_APPROVE, NOTIFY_ONLY, or SUGGEST (the human review queue) — and HITLHandler, the single owner of all FACT_DECISIONS writes, persists each decision born-complete with its tier. Human verdicts (CONFIRMED / OVERRIDDEN / ESCALATED) accumulate as free labeled eval data for Phase 6.

Tools in this phase
Pure Python rules — deliberately no LLMSnowflake (DECISIONS schema)
Why this, not that
Deterministic code over another LLM call — a real, recorded rejection

The recorded reasoning (PROJECT_STATUS.md, Phase 5): the two judgments are deliberately separated — "the agent should not be the arbiter of its own trustworthiness" — and the autonomy rules are deterministic code, not another LLM call, "because 'why did this auto-execute?' must be answerable with a rule citation, not a probability."

The tier boundaries themselves reason from recorded asymmetric error costs: a false ALLOW is unrecoverable money (so silent auto-approval is capped by amount), a false BLOCK is a recoverable inconvenience (so it executes but is always surfaced), and human attention is the scarce resource (so the SUGGEST queue holds only escalations and low-confidence calls).

What if not

An LLM assigning autonomy tiers: the recorded objection is exact — the audit answer to "why did this auto-execute?" becomes a probability instead of a rule citation. And letting the deciding agent grade its own trustworthiness is the specific conflict of interest the recorded design forbids.

No other alternative was recorded for this phase (e.g. no external workflow engine was compared) — said plainly.

Phase 6

Observability + evaluation

done · first honest scorecard: 6 transactions
What

Two things: a durable reasoning trace, and a measurement loop. AgentTraceWriter persists every step of every decision to FACT_AGENT_TRACES (INPUT → HANDOFF → REASONING → …, with per-step agent_name); the eval runner executes the full stack (orchestrate → tier → persist → trace) over a stratified half-fraud/half-legit sample and scores two orthogonal things: outcome accuracy against synthetic ground truth (ESCALATE deliberately scores NULL) and reasoning quality via an LLM judge. First batch: 6 transactions — decision accuracy 3/4 excluding escalations, escalation rate 2/6, pattern identification 2/6, mean judge score 0.88.

Tools in this phase
Snowflake (FACT_AGENT_TRACES · VARIANT)Groq LLM judge (temp 0)LangSmith (optional, env-gated)stratified sampler
Why this, not that
Own the compliance record; rent the dev telemetry

Recorded division of labor: FACT_AGENT_TRACES is the owned compliance record ("who decided and why", queryable next to the decisions); LangSmith is vendor dev-telemetry ("why was that prompt slow/wrong"), enabled by env var and a graceful no-op without an API key. Not either/or — both, with an explicit boundary.

Why an LLM judge here, when Phase 5 refused one

Recorded as a deliberate mirror image: governance chose rules-not-LLM because autonomy must be citable; evaluation chooses an LLM judge because grading free-text reasoning for groundedness/consistency/completeness "is exactly what rules can't do." The judge is same-model-family as the agents, with the self-preference caveat documented rather than hidden.

Two scoring rules with recorded reasoning

ESCALATE scores NULL: a deferral is neither right nor wrong — scoring it correct would let always-escalate game accuracy; scoring it wrong would punish calibrated humility. Escalation rate is reported as its own number instead. Sampling is stratified half-fraud/half-legit: an unstratified draw from the flagged pool (~2:1 legit, thanks to the hard-rule over-flagging) would mostly test false-positive handling and give almost no recall signal.

What if not

Unstratified sampling: per the recorded reasoning — a mostly-legit sample, so the eval would barely measure recall at all. (This is the same failure family as the "precision 1.0" incident on the story page: a metric computed on a sample that can't express the error you care about.)

Scoring escalations as right or wrong: per the record — either direction teaches the wrong lesson (gamed accuracy, or punished humility).

LangSmith as the only trace store: the compliance record — the thing that must sit queryable next to the decisions — would live in a vendor. That is the recorded boundary, not a recorded catastrophe claim.

Judge model choice: no alternative judge model was recorded — only the same-family self-preference caveat. Said plainly.

Honest caveat, preserved from the narrative: sample sizes have been small (as few as 6 transactions); real statistical confidence has NOT been established.

Phase 7

Agentic BI dashboard (NL2SQL)

done · guardrails verified fail-closed, 4/4
What

Natural-language analytics over the decision log: an English question becomes one Groq call producing structured {sql, explanation, chart_hint}; a code validator checks the SQL; only then does it execute against Snowflake, with a chart renderer that lets the LLM's hint propose and the actual result shape dispose. The generated SQL is always shown, expanded — an analyst who can't see the SQL can't catch a subtly-wrong query. Verified live: real questions returned true numbers from the persisted decisions, and all four hostile probes (DROP, a RAW.* read, semicolon smuggling, UPDATE) were rejected.

Tools in this phase
Groq (NL→SQL, one call)sqlglot (AST validator)StreamlitPlotlySnowflake
Why this, not that
The trust model: the LLM is an untrusted SQL author

Recorded explicitly: the prompt asks for good behavior (a quality measure); the validator enforces it (the security boundary) — only the validator is load-bearing. The table allowlist (only FACT_DECISIONS + FACT_FEATURE_SNAPSHOTS; RAW.* absent) is the PII boundary. Same judgment-from-models, invariants-from-code split as the Phase 4 router and Phase 5 rules.

AST validation (sqlglot) over the original regex guard — a recorded replacement
# Why AST, not regex — the concrete failure of the old approach:
#   A regex denylist of keywords is a blocklist, and blocklists
#   lose. `SELECT ... FROM IDENTIFIER('RAW.FACT_TRANSACTIONS')`
#   reaches the PII table with no forbidden keyword in sight;
#   `SELECT ... UNION SELECT ... FROM RAW...` hides the exfil in a
#   second branch; a table function `TABLE(FLATTEN(...))` is a data
#   source the keyword scan never modeled.
fraud_platform/bi_dashboard/sql_guard.py (verbatim excerpt)

The guard validates what the query is (an allowlist over parsed structure), not what strings it contains — and executes the re-serialized AST, so comment tricks and unicode lookalikes are normalized away before Snowflake ever sees the query.

Smaller recorded choices

Chart hint proposes, result shape disposes (code can veto down to table/metric, never erroring on odd shapes); DataFrames built manually instead of fetch_pandas_all() to avoid the connector↔pyarrow version coupling (pyarrow already pinned by Phase 1's Parquet writer).

What if not

Keeping the regex guard: this is the rare counterfactual the repo spells out with attack strings — IDENTIFIER() indirection, a UNION branch, table functions — each a way to reach PII with no forbidden keyword present. The regex guard is not hypothetical either: it was the actual first implementation, and sql_guard.py records replacing it.

Trusting the LLM's SQL outright: the four verified probes answer this empirically — without the validator, a DROP, a RAW.* read past the PII boundary, a smuggled second statement, and an UPDATE would all have reached the warehouse.

Streamlit / Plotly: no alternative UI or charting stack was recorded — said plainly.
